## 五、评审制度约定（后续沿用）

1. **需求评审**：需求文档每次改版都要走一轮全文一致性审核，审核结论写进 `Docs/需求.md` 的版本记录表，并在本台账追加一行；
2. **代码评审**：每个模块交付后由独立子代理做对抗式评审（重点是安全不变量 I-1 至 I-6 是否被破坏），发现写入本台账第三节；
3. **修复必须带证据**：每个修复都要有提交 hash，且提交信息写明"原来会怎样、现在怎么改"（例如"同毫秒撞名会覆盖账本"）；
4. **测试缺口显式登记**：发现"没有测试覆盖"要写进 `Docs/测试报告.md` 的缺口表，不允许静默；
5. **不编造**：无法确认出处的内容标"待确认"，不写"疑似已修复"这类模糊结论；
6. **HEAD 必须自洽**：任何提交后，`dotnet build` 与 `dotnet test` 都必须能独立通过，不允许靠未提交的工作区改动撑着（RC-12 的教训）。
