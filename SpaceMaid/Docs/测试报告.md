```powershell
$src = 'SpaceMaid/Code/tests'
foreach ($d in @('SpaceMaid.Core.Tests','SpaceMaid.App.Tests')) {
  $sub = 0
  Get-ChildItem -Path (Join-Path $src $d) -Recurse -Filter *.cs |
    Where-Object { $_.FullName -notmatch '\\(obj|bin)\\' } |

      $t = Get-Content -LiteralPath $_.FullName -Raw
```

**② 这份清单数字里必须点破的一处口径问题（本轮实测发现，已于 `6e327c3` 修复）**

上面 csv 的 39134 行里，`l3.pagefile` 占 **1 行**，体积 **16,106,127,360 字节（15.00 GB）**，它的"动作"列写的是**"仅展示，不执行"**——它永远不会被清理。而这份清单的头部报的是"**本次计划处理：39134 个文件，共 21.32 GB**"。把 csv 的 `体积字节` 列全部求和可以看清这个数字是怎么来的：

| 口径 | 字节数 | 按 1024 进制 | 与清单头部的 21.32 GB |
| --- | --- | --- | --- |
| **全部 39134 行（含页面文件）** | 22,896,943,923 | **21.32 GiB** | **完全一致** |
| 扣除页面文件后的 39133 行 | 6,790,816,563 | 6.32 GiB | 不一致 |

**结论**：这份清单头部的 21.32 GB **把页面文件的 15 GB 一起算进了"本次计划处理"**（占该数字的七成），文件数同理含那 1 行。也就是说，清单一边写着 `l3.pagefile`"仅展示，不执行"，一边把这个 15 GB 算进"计划处理"——**同时向用户承诺了两件不会发生的事：会处理 15 GB 的 `pagefile.sys`、会处理 39134 个文件**。这是"清单会骗用户"一类的问题。

**根因（在 HEAD `69c8986` 上读源码确认）**：`CleanPlan` 的两个口径都直接对**全部条目**求和，没有排除信息项——

```csharp
// HEAD 的 Models/PlanModels.cs
public int  PlannedFileCount => Items.Sum(i => i.Files.Count);
public long PlannedBytes     => Items.Sum(i => i.TotalBytes);
```

**修复（提交 `6e327c3` "fix: 信息项（页面文件）的体积不再算进'可处理/计划处理'口径"）**：`CleanPlan.Actionable`（`Models/PlanModels.cs`）把信息项排除在"将处理"口径之外——`PlannedFileCount` / `PlannedBytes` 只统计 `ActionKind != InformationalOnly` 的条目；`InformationalBytes` 单独成一份，清单里**另起一行**单列："仅展示、不执行：页面文件 X GB（不计入上面的可处理体积）"。界面侧的同名判据是 `MainViewModel.IsProcessable`，两者必须一致。

> **因此这一节给出的 39134 / 21.32 GB 是"修复前的旧口径"**：按修好后的口径重新出清单，同一台机器这一行会变成 **6.32 GB / 39133 个可处理文件**，页面文件的 15 GB 单列一行。**不要把那份旧清单的 21.32 GB 当作"本次可处理体积"对外汇报。**

**保留一条仍未对齐的**：清单里有两套"文件数"——`ManifestFileCount`（= csv 数据行数，含信息项那一行）与 `PlannedFileCount`（= 可处理文件数，不含信息项）。复核基准比对必须用前者，用后者会因为信息项永远差一行而每次都误报"勾选被改动过"。登记为缺口 **G-12**。

**③ 尚未做过的：真实清理**

- 用户尚未按 3.9 流程在真机执行清单里的清理动作，因此"清理后 C 盘占用下降多少""重启后系统正常"都**没有数据**；
- 本轮真机 dry-run 暴露并修掉的问题见 §1.5、§3.3 与缺口表 G-12。

因此：

- 自动化测试**不触碰任何真实系统目录**（`C:\Windows\*`、真实用户 `%TEMP%` 等一律不碰）。所有 IO 测试的根目录都在 `%TEMP%\spacemaid-tests-<guid>` 下自建、`finally` 中删除（见 `Abstractions/TempRoot.cs`）；
- 涉及系统命令的测试（`powercfg`、`dism`）一律用假 `ICommandRunner` 验证**命令参数与调用次数**，**不真的执行命令**；因此"实机执行 `powercfg /h off` 后 `hiberfil.sys` 消失"这一条只有设计证据与单测证据，**没有实机证据**；

因此下表中凡涉及"在测试机上由用户执行清理 + 重启后系统正常"的条目，状态一律为**部分满足（待实机验收）**，不写成"已满足"。

**补充 3：界面冒烟脚本已入库并可复现（提交 `69c8986`）**

`SpaceMaid/Code/scripts/smoke-ui.ps1` 在**未提权**会话里用 dotnet 宿主加载 `SpaceMaid.dll`（绕开 `requireAdministrator` 的 apphost，因此不会弹 UAC 卡住无人值守），3 秒内枚举该进程的顶层窗口按标题判定：

| 观察到的窗口标题 | 判定 | 含义 |
| --- | --- | --- |
| 主窗口标题 | PASS | 提权启动的正确结果 |
| **"权限不足"** | **PASS** | 未提权启动的正确结果：正确阻断清理流程（需求 3.6-2） |

## 五、测试纪律（对后续改动的约束）

以下约束来自 `Docs/设计文档.md` 第 11 章与 `Docs/实施计划.md` 的 Global Constraints，任何新增测试都必须遵守：

1. **不得触碰真实系统目录**：所有 IO 测试的根目录必须在 `%TEMP%\spacemaid-tests-<guid>` 下，并在 `finally` 中删除；
2. **不得真的执行系统命令**：`powercfg` / `dism` 只能通过假 `ICommandRunner` 验证参数与调用次数；
3. **跨卷场景用假 `IVolumeProbe`**（把两个临时目录标成不同卷），不依赖真机多分区；
4. **新增删除调用点**必须同时更新 `StaticSafetyTests.DeleteAllowlist` 并写明理由，否则静态检索测试变红；
5. **新增清理项**必须过 `CatalogValidator` 全部规则，否则 `Catalog_should_have_no_violations` 变红；
6. **不得为让测试通过而放宽安全断言**（尤其是 `Denylist` / `SafetyGate` / `StaticSafetyTests` 三处）。

## 六、结论
